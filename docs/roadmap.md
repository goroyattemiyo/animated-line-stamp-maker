# 開発ロードマップ

## 文書の役割

この文書は実装順と各段階の完了条件だけを管理する。

機能要件、内部構成、データモデル、画像処理アルゴリズム、テスト方針は `docs/app-spec.md` を正本とする。重複する詳細設計は本書へ増やさない。

## 基本方針

```text
入力と出力の技術検証
  ↓
安全なアプリ基盤
  ↓
分割・除去・共通キャンバス
  ↓
位置調整・タイムライン
  ↓
APNG生成・独立検証
  ↓
プロジェクト保存
  ↓
セット制作支援
```

## Phase 0: 生成仕様とFixtureの固定

### 作業

- GPT出力を横4列×縦2行へ統一
- トンボ付き正常サンプルを複数生成
- 不良サンプルを収集
- 正常な8分割結果をFixture化

### 完了条件

- 固定グリッドで8セルを判別できる
- トンボの一部欠損時も処理方針が決まっている
- 正常・警告・不採用の例をテスト入力として保存できる

## Phase 1: 技術スパイク

UI本実装より先に、配布後も画像処理とAPNG生成が動くかを確認する。

### 作業

- electron-vite + React + TypeScriptの最小構成
- electron-builderによるWindowsパッケージ
- Sharpのcrop・resize・RGBA取得
- Worker内でのSharp実行
- APNGエンコーダ候補の比較
- APNGチャンク検査と再デコード

### 完了条件

- Windowsパッケージ後もSharpが動く
- 透過・5〜20フレーム・delay・loopを保持したAPNGを生成できる
- 生成APNGを別処理で再検査できる
- 採用するAPNGエンコーダと代替案が決まる

## Phase 2: 安全なアプリ基盤

### 作業

- Main / Preload / Renderer / Workerの分離
- `nodeIntegration: false`
- `contextIsolation: true`
- `sandbox: true`
- 型付きの限定IPC
- ファイルダイアログとドラッグ&ドロップ
- 入力上限とPNG署名検査
- エラーコードの共通化

### 完了条件

- PNGを安全に読み込める
- RendererからNode.js APIへ直接アクセスできない
- 不正形式・巨大画像・復号失敗を適切に停止できる
- Image Workerのジョブをキャンセルできる

## Phase 3: グリッド分割

### 作業

- 均等4列×2行の初期境界
- 全画素を欠落なく8セルへ分割
- 元シート上の境界オーバーレイ
- 縦3本・横1本の手動調整
- 均等配置へ戻す
- サムネイル表示
- 連番PNGの仮出力

### 完了条件

- 割り切れない解像度でも全画素を重複・欠落なく分割できる
- フレーム順が01〜08で正しい
- 不均等な生成シートを手動補正できる

## Phase 4: マーカー除去と共通キャンバス

### 作業

- 全体トリム比率
- フレーム別上書き
- 除去範囲オーバーレイ
- 内容切断警告
- アルファ外接矩形
- 全フレーム共通外接矩形
- 最低限の安全余白

### 完了条件

- L字トンボを一括除外できる
- トンボなし入力も処理できる
- キャラクターが切れそうな場合に警告できる
- 個別トリミングによるガタつきを発生させない

## Phase 5: フレーム編集とプレビュー

### 作業

- 1px単位の手動X/Y調整
- オニオンスキン
- フレーム並べ替え
- 複製・削除・逆順・往復
- 表示時間編集
- 1〜4秒への正規化
- 1〜4ループ
- 白・黒・市松背景プレビュー

### 完了条件

- 5〜20フレームで編集できる
- 指定した順序・時間・ループで再生できる
- 1フレーム目を明確に確認できる
- 意図しない位置ずれを手動で修正できる

## Phase 6: LINE出力パイプライン

### 作業

- 共通倍率による最大320×270以内への変換
- 出力寸法の偶数化
- RGBA 8bit統一
- APNG生成
- 一時ファイル保存
- PNGチャンク検査
- 全フレーム再デコード
- 検査成功後の原子的rename
- 1MB容量判定

### 完了条件

- 透過APNGを生成できる
- フレーム数・delay・loop・寸法が設定どおりである
- 全フレーム同一や通常PNGへの誤出力を検出できる
- 検査失敗ファイルを完成品として残さない

## Phase 7: LINE仕様チェッカー

### 作業

- 仕様値を1か所へ集約
- Error / Warning / Infoの分類
- フレーム数
- 1ループ時間
- ループ回数
- 総再生時間
- 寸法
- RGB・透過
- 容量
- 連続する同一フレーム
- 先頭フレーム確認

### 完了条件

- 書き出し不可条件と注意条件を区別できる
- 公式仕様値更新時に画像処理コードを修正せず対応できる

## Phase 8: プロジェクト保存

### 作業

- `.alstamp.json`保存
- schemaVersion検証
- 再読込
- 元画像SHA-256照合
- 元画像再指定
- 未保存確認
- Undo/Redoの基盤

### 完了条件

- アプリ再起動後も編集状態を復元できる
- 元画像変更・欠損を検出できる
- 元画像を上書きしない

## Phase 9: Windows配布品質

### 作業

- Unit Test
- Fixture Test
- APNG Integration Test
- Playwright E2E
- Windows GitHub Actions
- NSISまたはportable zip
- 実機スモークテスト
- 処理時間計測

### 完了条件

- typecheck・lint・test・build・packageが合格する
- Windows実機で入力からAPNG出力まで完走する
- 基準画像で性能目標を大きく下回らない

## Phase 10: セット制作支援

単体APNGの品質が安定してから着手する。

### 候補

- 8個・16個・24個セット管理
- 複数シート一括入力
- 共通設定の一括適用
- メイン画像生成
- トークルームタブ画像生成
- ファイル名整形
- ZIP出力
- 進捗一覧

## Phase 11: 高度機能

必要性と精度を検証してから追加する。

- マーカー自動認識
- 自動位置合わせ候補
- 透過ゴミ検出
- 容量最適化
- 明示的な減色
- フレーム補間
- Web版
- macOS版

## 着手順

直近は次の順とする。

1. 正常・不良Fixtureの収集
2. Electron・Sharp・Worker・APNGの技術スパイク
3. パッケージ後のAPNG再検査まで通す
4. その結果をもとにプロジェクト初期構成を確定
5. グリッド分割UIへ進む

UIを先に作り込み、後からAPNGライブラリやネイティブ依存で構成を崩すことは避ける。
